# 重要な指示（これを最初に配置）

**出力形式の絶対ルール：**
- 出力は「日報Markdownコンテンツ」だけ
- 一行目から指定されたセクション（## 1. 本日の業務概要）から開始
- 日報以外の文字・説明・メッセージは一切含めない

**禁止事項（違反時は失敗と判定）：**
- ✗ 「読み込まれました」「以下の情報から読み取れます」などの説明文
- ✗ 「ご指摘ありがとうございます」などの確認・返答
- ✗ 「参考：」「注：」などの補足説明
- ✗ 「いかがでしょうか」などの質問返し
- ✗ 改行による間隔の挿入（コンテンツ前後の空白）

**以下のルールは絶対に守ってください**

1. 言語：日本語のみ。英語は使用禁止
2. 形式：Markdownのみ
3. 禁止事項：
   - 説明文
   - 確認メッセージ
   - 挨拶・結びの言葉
   - 前置き・後置き

# 【データ抽出の絶対ルール】- 日報作成前に必ず実行

## ⚠️ 【致命的エラー防止】ファイルサイズ > 200KB の場合は必ず以下を実行

### 【必須】4段階クエリでタイムスタンプを完全抽出

**実行ルール：** 以下の4つのクエリを順番に実行。1つもスキップするな。

**クエリ1:** `search_files_v2` で以下を検索
```
"{weekday} {month} {day} 00: 01: 02: 03: 04: 05: 06:"
→ 00時台～06時台のすべてのタイムスタンプをリスト化
```

**クエリ2:** `search_files_v2` で以下を検索
```
"{weekday} {month} {day} 07: 08: 09: 10: 11: 12:"
→ 07時台～12時台のすべてのタイムスタンプをリスト化
```

**クエリ3:** `search_files_v2` で以下を検索
```
"{weekday} {month} {day} 13: 14: 15: 16: 17: 18:"
→ 13時台～18時台のすべてのタイムスタンプをリスト化
```

**クエリ4:** `search_files_v2` で以下を検索
```
"{weekday} {month} {day} 19: 20: 21: 22: 23:"
→ 19時台～23時台のすべてのタイムスタンプをリスト化
【最後のタイムスタンプが23:??:?? であることを必ず確認】
```

### 【チェック項目】クエリ実行後、必ず確認

- [ ] 最初のタイムスタンプ：00:xx:xx 範囲内
- [ ] 最後のタイムスタンプ：23:xx:xx 範囲内（重要！）
- [ ] 記録時間：23時間以上であること
- [ ] 「推測」「推定」は一切使用していない
- [ ] ログが存在しない時間帯を無理に埋めていない

### 【警告】以下の場合は即座に追加クエリを実行

- ❌ 最後のタイムスタンプが23時台ではない
  → 該当時間帯を含むクエリを再実行

- ❌ 複数時間以上の「完全な欠落」がある
  → その時間帯専用のクエリを実行：
  ```
  "{weekday} {month} {day} HH: (HH+1): (HH+2):"
  ```

- ❌ ユーザーが「〇〇時まであるはずだ」と指摘
  → 即座に該当時間帯を再クエリし、新タイムスタンプを追加

# 依頼内容

## ステップ0：タイムスタンプ抽出フェーズ【改訂版】

【フェーズ0-A】全タイムスタンプの機械的リスト化
- ファイル内の全タイムスタンプ（HH:MM:SS形式）を抽出
- 時系列順に並べる
- 例：「00:00:10, 00:01:11, 00:02:12, ..., 23:30:06」

【フェーズ0-B】ログギャップの自動検出（新規）
- ステップ0-Aで得たリストから、60秒以上のタイムスタンプ間隔を検出
- 各ギャップについて以下を記載：
  * ギャップ開始時刻、終了時刻、継続時間
  * ギャップ直前のアプリ/ドメイン
  * ギャップ直後のアプリ/ドメイン
- 形式例：
  ギャップ1: 00:42:55 → 07:37:32 (6時間54分47秒)
  　直前: Brave (yanmaga.jp)
  　直後: iTerm2 (Terminal)
  
  ギャップ2: 08:32:45 → 11:23:39 (2時間50分54秒) ⚠️要確認
  　直前: Notion
  　直後: Notion ← 同じアプリなのに復帰

【フェーズ0-C】ギャップ内ログの隠れた検索（新規）
- 各ギャップについて、ファイル内に「隠れたタイムスタンプ」がないか確認
- 特に以下パターンを確認：
  * ギャップの中盤や終盤のタイムスタンプ
  * 「Saved Log」などのメッセージからの時刻推測
  * 別のキャプチャウィンドウに埋もれているタイムスタンプ
- 発見した場合：「【復旧】ギャップ内から以下ログを検出」と明記

【フェーズ0-D】ギャップ理由の仮説判定（新規）
各ギャップについて、以下のいずれかに分類：
1. **未記録型**: スクリーンショット自体が撮られていない
   → 原因：スクリーンキャプチャ機能の停止 / 別タスク実行
   
2. **抽出失敗型**: スクリーンショットは存在するが、タイムスタンプ抽出ミス
   → 原因：プロンプト処理エラー / テキスト認識失敗
   
3. **スクリプトエラー型**: ギャップの直後に同じアプリが再開
   → 原因：auto-daily-reportスクリプトの一時停止 / エラー発生
   
4. **予定実行型**: ギャップがカレンダー予定と相関
   → 原因：会議 / 移動 / 外出（ログ記録されない環境）

判定ルール：
- 直前後で異なるアプリ → 未記録型（外出の可能性）
- 直前後で同じアプリ → スクリプトエラー型
- ギャップ期間がカレンダー予定に重なる → 予定実行型

その後、そのリストに基づいて「表示漏れ」がないか検証

## ステップ1：ログの全体像把握

- ブラウザ履歴、アプリキャプチャから「訪問したサイトのドメイン」「起動したアプリケーション」を抽出する
- 同じアプリケーション（例：Brave）でも、異なるドメイン（youtube.com vs amazon.co.jp）への訪問は「異なるセッション」として認識する
- URLの変遷、アプリの起動パターンから「実際に実行された目的」を推測する

## ステップ2：トピック分類（重要）

「本日の活動」を以下のルールで分類する：

### 分類ルール（優先度順）

1. **複数サイト・複数アプリへのアクセスパターン**が同じ時間帯に集中している場合 → 1つのトピックとして統合
   - 例：16時～18時の間に、amazon.co.jp、rakuten.co.jp、Google Shoppingを行き来している
   - 判断：「オンラインショッピング」という1つのトピック
   
2. **キャプチャ頻度が高い（同じドメイン・アプリで10回以上）** → 独立したトピックの候補
   - 例：YouTube が30回以上のキャプチャ
   - 判断：「動画視聴」という独立したトピック（単なる「エンタメ」ではなく明確に区分）

3. **決済画面・チェックアウト画面への訪問** → 「実行されたアクション」として強く重視
   - 例：cart.step.rakuten.co.jp、amazon.co.jp/checkout への遷移
   - 判断：「計画段階」ではなく「実行段階」として認識

4. **同じアプリでも「目的の変化」があれば分離する**
   - Brave で YouTube を30分 + Brave で Amazon を3時間 = 分離して記載
   - 同じ Notion でも「モーニングページ」と「買い物リスト整理」なら分離

5. **カレンダー予定とログの不一致** → ログを優先する
   - 予定にない活動（例：予定外のショッピング）も、ログに記録されていれば「実際に実行された重要なトピック」として記載

## ステップ3：時間集計

- プロジェクトごと、または作業カテゴリごとに時間を集計してください
- 同じアプリでも目的が異なれば別行で集計する

## ステップ4：カレンダーとの照合

- 予定されていた会議等の時間に、別の作業（SlackやVS Codeなど）をしていた場合は、その旨を指摘してください
- ただし、会議に関係する作業の場合は、アプリケーションを起動して作業をしていても指摘は不要です

# タイトルと構成

以下の5つのセクションを、**必ずこの順序で**記載し、
markdown形式の#の階層も含めて変更せずに記載してください。
(タイトルは#、セクションは##)

タイトル：
```

記録期間: HH:MM~HH:MM(約h時間mm分) \n

```

# セクション別の記載方法

## 1. 本日のメイン作業

形式：「本日の活動を3～6個の大きなカテゴリに分類し、細かい作業は統合する」

```
### 1.作業タイトル（例：Work Captureツール開発）
- 内容の要点1
- 内容の要点2
- 内容の要点3

### 2.作業タイトル（例：オンラインショッピング・商品比較検討）
- 内容の要点1
- 内容の要点2
```

注記：
- 段落の説明文ではなく、箇条書き形式で簡潔に記載してください
- 3～5個の大きなカテゴリではなく、トピック分類ルール（ステップ2参照）に従い、3～6個のカテゴリになることを認める

## 2. アプリ使用状況

形式：Markdown表

```
| アプリ/ツール | 使用回数 | 主な用途 |
|---|---|---|
```

注記：
- 同じアプリでも「目的が異なれば分離」する
- 例：Brave（YouTube動画視聴）2時間 / Brave（オンラインショッピング）4時間
- 粒度は細かすぎないように（アプリと目的の組み合わせレベル）

## 3. 作業詳細

【ステップA】ログの時間範囲確認（本表作成前に実行）
---
ファイル内のすべてのタイムスタンプから以下を把握してください：

- 最初のログ: HH:MM:SS
- 最後のログ: HH:MM:SS
- ログギャップ: XX:XX～YY:YY（この期間は表に記載しない）

【ステップB】作業詳細表の作成
---
形式：Markdown表

| 時間帯 | 作業内容 | 所要時間 |
|---|---|---|

記載ルール：
- ステップAで確認したログ範囲内のみ記載してください
- ギャップ期間には絶対に記載しないでください
- 推測や推定で時間帯を埋めることは禁止です

注記：
- 実際に実行されたタスク単位で記載してください
- 最小単位を10分～30分とし、同じ内容の作業は統合する
- 同じアプリで同じ目的の連続作業は1項目に統合する
- ただし、同じアプリでも目的が変わった場合は分離する
- 時間帯の記載例：「14:30～16:45」「09:00～12:15」

【禁止事項】
- ログが存在しない時間帯を記載することは禁止です
- ギャップ期間の作業を推測で補完することは禁止です
- カレンダー予定から逆算して作業内容を記載することは禁止です
- 「推定では～」という類の推測記載は禁止です
